## Priority 2 — Master jobs (≈ 1 week)

Data flows correctly (WipMasterSub → `masterJobId`/`IsMasterJob`/`IsSubJob` → grouped UI with family scheduling buttons). The gap is that **the engine has no idea master/sub relationships exist**.

**2.1 Add master-job fields to the backend `Job` type** *(S)*
`masterJobId`, `isMasterJob`, `isSubJob` ride along untyped from the SQL today. Add them to `backend/src/types.ts` and the shared frontend type so the engine can use them.

**2.2 Job-level precedence in the greedy engine** *(M — the core item)*
In SYSPRO, sub-jobs feed the master job. Today the engine schedules each family member independently, so a master job can start before its sub-jobs finish. In `SchedulingEngine`:
- Forward: schedule sub-jobs first; the master's earliest start = max(sub-job end dates).
- Backward: master scheduled first; sub-job due dates = master start.
- Emit a `ConstraintViolation` (`MasterJobPrecedence`) when the horizon can't accommodate the chain.

**2.3 Same constraint in CP-SAT** *(M)*
Add `master_job_id` to the solve request and an inter-job precedence constraint in `cp-sat/main.py` (end of every sub-job op ≤ start of first master op).

**2.4 Server-side family completion** *(S)*
When `selectedJobIds` contains a master, auto-include its sub-jobs (and warn when a sub-job is selected without its master). Today family completeness depends on the frontend building `familyIds` correctly.

**2.5 Align the drag-drop "schedule master group" path** *(S)*
`App.tsx:2051` (`mode === 'master'`) places family members near anchor dates with `autoScheduleDroppedJob` — no precedence. Once 2.2 lands, route this through `/schedule/generate` with the family's IDs instead.

**2.6 Tests** *(M)* — greedy: family ordering forward + backward, violation emission; CP-SAT: payload carries `master_job_id`; route: family auto-completion. ~10 cases.

## Priority 3 — Manual scheduling (≈ 1 week)

The board interaction layer is strong (drag with capacity-aware slot finding, tail re-flow, multi-select, keyboard nudges, undo/redo). The critical bug is persistence.

**3.1 Fix the lost-edits bug** *(S — highest-value fix in this plan)*
`handleScheduleBoardOperationMove` never changes `scheduleSource`. If the board is showing a SYSPRO-derived schedule (`scheduleSource === 'syspro'`):
- the autosave effect (`App.tsx:684`) skips saving (it requires `'session'`), and
- the rebuild effect (`App.tsx:697`) regenerates the schedule from `openJobs` on the next refresh, **silently wiping the manual edit**.

Fix: call `setScheduleSource('session')` (or add a `'manual'` source) at the end of every manual mutation (board move, keyboard nudge, pin, context-menu actions), so edits persist via `/schedule/save` and survive refreshes.

**3.2 Implement or delete `POST /api/jobs/:jobId/update-schedule`** *(S)*
`jobs.ts:604` returns success without writing anything. Nothing calls it — delete it, or implement it against `sch_` tables if you want an API for external date updates. A silent-success endpoint is a trap.

**3.3 Machine-level reassignment on drop** *(M)*
Moves only change `workcentreId`; `resourceId` is preserved by design (`App.tsx:2415`). The alternative-machine groups feature (`/resources/alternatives/groups`) exists but drag-drop can't switch machines within a group. Add per-machine lanes drop support: when dropped on a specific machine lane, reassign `resourceId` if the machine is in the op's workcentre or its alternative group.

**3.4 Validate manual placements against calendars** *(M)*
The board's `findEarliestSlot`/`calculateProductiveEndMs` handle capacity and productive time, but confirm shift-calendar boundaries are enforced the same way the engine does (or show an "outside shift" warning tag on the bar instead of blocking).

**3.5 Tests** *(M)* — the persistence fix (3.1) needs a regression test: move op → source flips → autosave fires; rebuild effect doesn't clobber. Plus slot-finder unit tests extracted from App.tsx (the interval logic is pure and easily testable if lifted into `utils/`).

was already compensating for exactly this. On a mismatch, `jobsInRun.has(masterId)`
silently failed and precedence was skipped with no warning. A second gap: the APS-views
path (`USE_APS_VIEWS=true`) never selected the master fields at all.

- **`utils/jobIdNormalization.ts` (new):** `canonicalJobKey` (trim, numeric ids lose
  leading zeros) + `resolveMasterLinks` rewrites every `masterJobId` to the exact
  `jobId` string of the loaded master and repairs `isMasterJob`/`isSubJob` flags.
  Called at the end of BOTH `getOpenJobs` paths. 11 unit tests.
- **APS-views query** now selects `ParentOrdNumber as masterJobId` (populated from
  `WipMaster.HierarchyJob`) + derived `IsSubJob`.
- **Manual drag & drop guards** (`frontend/src/utils/masterSub.ts`, new — also absorbs
  App.tsx's master-link/root helpers as the single source of truth): dropping a MASTER
